# Domain concept and consumer inventory

The domain migration is **not complete**. Twenty-one concrete authoring classes and the Entity foundation
exist; none of that establishes universal migration of their runtime counterparts or consumers.
This inventory expands the baseline for [migration gates 0–5](entity-architecture-and-migration.md#migration-gates).
Experience and engine feature development remains paused. Adapting existing runtime behavior later
is migration work; adding mechanics, experiences or automatic reactions is not authorized by this inventory.

## Authority, method and status

B06 completes the D01 foundation and D14/D23 catalog portion of I01/I04. The older
checklist spans wider authoring/runtime work; remaining obligations are mapped to
B07/B09–12 in BACKLOG.md. Feat, Heritage and Discipline are permanently excluded;
older references below do not authorize their implementation. B08 completion and
its explicit B10 boundary are also recorded in BACKLOG.md.

Read `docs/README.md` first. Common TypeScript contracts remain authoritative; canonical architecture
supplies ownership and accepted target behavior. Inspected all 39 files in `packages/common/src/types`,
all domain source exports, generic resource mappings, Prisma model families, API policy entry points,
common rules/spatial implementations and browser consumers. Evidence below names source files and
key symbols rather than treating documentation or a class name as proof of completion. This is a
source inventory, not a new test run or a live-data audit. Previously passing tests are delivery
history, not evidence that all consumers have migrated.

Status vocabulary:

- **Partial:** concrete class exists, but workflows, runtime lifecycle or duplicate consumers remain.
- **Unmigrated:** current contract/behavior exists without its executable owning entity.
- **Value/contract:** DTO, identity, expression, projection, immutable capture or owned value; no
  independent entity is implied. Its owning entity must still own concept-specific validation/codecs.
- **Boundary:** application/infrastructure responsibility retained outside entities.
- **Deferred/retired:** explicit accepted deferral or compatibility-only format; never silently reactivated.

Proposed owner names below are migration assignments, not additions to the authoritative type model.
Separate classes are warranted by identity, state lifecycle and behavior; every interface does not
need a class, database row or new identifier. In particular, Objects, Traps and Hazards are Item
families/capabilities under accepted architecture; older Object/Hazard contracts need explicit
compatibility handling, not automatic promotion to peer roots.

### Reachability and persistence qualifications

- There is no separate engine workspace; the existing pure engines are in common's `rules` directory.
- The original inventory found no browser entity consumers. Profession editors now import `@aow/domain`
  for class-owned construction and local grant validation; no browser `state$` adoption is implied. API entity usage is
  concentrated in World/Codex/proposal adapters and Attribute compilation, with no application
